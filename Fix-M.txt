FIX-M — Fixing the Userspace Test Gaps: Vacuous Assertion + Correlation-Group Wiring

Status: Implemented, compiled, and test-validated (9/9 tests passing on Rust 1.75, cargo test, for the underlying digital-twin logic). The Python/PyO3 boundary itself is not compiled or executed in this environment — see "Scope and honesty about validation" below for exactly what that means and doesn't mean.

This patch closes two separate gaps identified in review of qib/src/ai/digital_twin.rs and tests/test_calibration.py.

Gap 1 (FIX-M1): a vacuous test hiding a real epsilon-floor bug

test_std_dev_never_zero_on_confident_link's assertion was:

assert ls.fidelity_std > 0.0 or True 

That's True unconditionally, regardless of fidelity_std's actual value — it cannot fail no matter how badly the code regresses. It was also hiding a real bug: the floating-point path computed fidelity_std = self.m2.sqrt().max(0.0). A floor of 0.0 is not a floor. qib-schema's FIDELITY_VARIANCE_EPSILON_FP_BITS (FIX-B) only protects the fixed-point kernel path — the Python-facing floating-point path never had an equivalent.

A minimal repro confirms both halves of this directly:

fidelity_std after 100,000 identical observations: 0 Would 'assert std > 0.0 or True' ever fail here? No -- it can't, regardless of std's value. Would 'assert std > 0.0' (the real check) fail here? true 

For a link pinned exactly at the twin's initial mean, fidelity_std collapses to a literal 0.0 — precisely the condition that makes a downstream Z-score divide by zero — and the original test's assertion would have sailed through regardless.

Gap 2 (FIX-M2): the correlation-group mechanism was unreachable

TestCorrelationGroups::test_group_failure_boosts_peer_safety_tax called twin.observe(...) and twin.record_group_failure(42), but nothing in the exposed API ever set a link's correlation_group_id. record_group_failure worked, correlation_group_boost() worked, but with correlation_group_id permanently None, the boost could never apply to any link — Improvement 2-B's entire spatial-correlation safety-tax mechanism was dead code from Python's perspective, and the test asserting it worked was testing something that structurally could not happen.

The fix

FIX-M1: apply a real epsilon floor (FIDELITY_VARIANCE_EPSILON = 1e-6) to the floating-point path, mirroring FIX-B's intent in the domain the fixed-point constant doesn't reach. Rewrite the test assertion to actually check fidelity_std > 0.0.

FIX-M2: add set_correlation_group(link_id, group_id), the call that was missing from the API entirely. Update the test to call it before recording group failures, matching what it was clearly trying to test.

The two most important tests:

fidelity_std_floor_holds_even_with_thousands_of_identical_observations — observes the exact same value as the twin's initial mean 50,000 times (the fastest way to drive m2 toward literal 0.0) and asserts fidelity_std still never drops below the epsilon floor. This is the Rust-level regression test for FIX-M1.

set_correlation_group_then_group_failure_raises_safety_tax — the direct regression test for FIX-M2: warms up a link to low std_dev, links it to group 42, confirms 2 failures aren't enough, then confirms the 3rd crosses CORRELATION_FAILURE_TRIGGER and flips safety_tax to true.

Also notable: while building these tests, warming a link up with only 50 observations (matching a number that seemed reasonable from the original review) turned out to leave fidelity_std still above the safety-tax threshold on its own — 50 observations isn't enough for the EWMA to converge from the initial mean (0.5) to the observed value (0.95) at EWMA_LR = 0.05. The tests use 200 observations instead, which converges fidelity_std to ≈0.0027, confirmed numerically:

n=25 std=0.201470 n=50 std=0.119927 n=100 std=0.034523 n=200 std=0.002664 

This mattered for correctness of the test, not the fix: without enough warm-up, group_failure_has_no_effect_until_link_is_linked_to_the_group would have failed for the wrong reason (residual std_dev, not a correlation-group bug), which would have been a confusing false positive pointing at the wrong mechanism.

Scope and honesty about validation

This crate compiles and tests the core digital-twin logic — the actual bug and actual fix for both gaps — as a plain Rust library with no PyO3 dependency. What's validated by cargo test above is real and specific: the epsilon floor holds under adversarial conditions, and the correlation-group mechanism only affects links explicitly linked to a group.

What is not validated here: the actual PyO3 bindings (#[pyclass]/#[pymethods] on ProbabilisticDigitalTwin and LinkState, a set_correlation_group method exposed to Python, a safety_tax property getter) and the corrected tests/test_calibration.py file were not compiled or run against a real Python interpreter through the actual extension module — building that requires maturin/setuptools-rust and a matching Python ABI, which isn't set up in this environment. The Python test file above was checked with python3 -m py_compile (confirms it's syntactically valid Python) but not executed against real bindings.

Treat this the same way as FIX-K's TLA+ boundary: the logic that can be compiled and tested in isolation was, exhaustively; the platform-specific wiring around it (there, a hardware reset; here, a PyO3 extension module) is described and reasoned about precisely, but the claim of "tested" stops at that boundary and says so explicitly rather than implying more than was actually run.

What did not change

FIX-A's EWMA update formula itself (m2 = (1-lr)·m2 + lr·delta1·delta2) is untouched — this patch only changes what happens to the result (.max(FIDELITY_VARIANCE_EPSILON) instead of .max(0.0)), not the variance computation.

FIX-C's DashMap entry-API pattern for observe() is untouched; set_correlation_group() uses the identical pattern for consistency and to avoid reintroducing the read-modify-write race FIX-C fixed.

record_group_failure() and correlation_group_boost() are unchanged — they always worked correctly; the gap was entirely on the "how does a link get linked to a group in the first place" side.
