FIX-L — Removing the Redundant AttestationCap Wrapper (and the Leak It Was Hiding)

Status: Implemented, compiled, and test-validated (39/39 tests passing on Rust 1.75, cargo test). Sits alongside FIX-H2/FIX-G/FIX-J/FIX-K already applied to this crate.

The redundancy

FIX-G originally put valid_until_ns on a standalone AttestationCap wrapper in attestation.rs, with its own is_valid() / assert_cap_not_expired() helpers:

// OLD wrapper — a second, disconnected copy of the expiry fact pub struct AttestationCap { pub capability: Capability, pub valid_until_ns: u64, } impl AttestationCap { pub fn is_valid(&self, now_ns: u64) -> bool { now_ns < self.valid_until_ns } } 

A later patch moved valid_until_ns directly onto CapabilityKind::Attestation in capability.rs, because that's the type require_attestation() — the actual authorization gate every other subsystem calls — checks. Once that happened, nothing in the real enforcement path ever read AttestationCap, is_valid(), or assert_cap_not_expired() again. They kept compiling, kept looking authoritative, and were completely disconnected from the system's actual behavior — exactly the kind of drift that causes a future maintainer to "fix" the wrong copy.

The bug the redundancy was hiding

Worse, the old renew_attestation re-verified fresh TEE evidence (correct) but then called verify_and_mint_cap() again — which mints a brand-new capability rather than extending the lease on the existing one:

// OLD (buggy) renewal pub fn renew_attestation( pid: u32, report: &AttestationReport, now_ns: u64, ) -> Result<AttestationCap, KernelError> { verify_and_mint_cap(pid, report, now_ns) // <-- mints #2, #1 untouched } 

The original capability was never revoked, so every "renewal" actually left two live attestation capabilities for the same enclave — one silently orphaned in the table forever. A minimal repro of the exact old logic confirms this directly:

live capabilities for pid 500 after mint: 1 live capabilities for pid 500 after 'renewal': 2 (BUG: should still be 1) original capability idx 0 still present: true new orphaned capability idx 1 also present: true 

That's a capability-table leak (every renewal over a node's uptime burns another slot against the MAX_CAPS = 256 budget) and a needlessly widened attack surface: whoever held the original index retains valid access for the rest of its own lease, regardless of anything the "renewal" was supposed to change.

The fix

Delete AttestationCap, is_valid(), assert_cap_not_expired(). capability::require_attestation() already does everything they did, against the copy of valid_until_ns that's actually enforced.

verify_and_mint_cap() now mints directly into the capability table via capability::insert_capability and returns the resulting slot index, instead of handing back a value nothing else reads.

renew_attestation() now takes the existing capability's index, re-verifies fresh evidence, and extends that same slot's lease via capability::renew_attestation — no second capability is ever minted.

Added capability::count_live_attestations_for(pid), a small diagnostic used by the regression test to make the leak directly observable as an assertion rather than something you'd only notice by eventually exhausting the capability table.

All 34 pre-existing tests (FIX-H2, FIX-G, FIX-J, FIX-K — untouched by this patch) pass unmodified, plus 5 new attestation tests:

renew_attestation_extends_the_same_capability_without_leaking_a_second_one — the direct regression test for this bug: mints, renews, and asserts count_live_attestations_for stays at exactly 1 throughout, while access genuinely extends past the original lease's expiry.

multiple_renewals_never_grow_the_live_count — renews the same capability 5 times in a row and asserts the live count never exceeds 1 at any point, not just after a single renewal.

renew_attestation_on_a_revoked_slot_fails_cleanly — renewing an already-revoked capability correctly fails rather than silently minting a fresh one.

mint_then_require_attestation_succeeds_within_lease / mint_then_require_attestation_fails_once_lease_expires — confirm verify_and_mint_cap's output still plugs into require_attestation exactly as before; this cleanup doesn't change first-time minting behavior at all.

To confirm the regression test is meaningful (i.e. it would have failed against the pre-fix code), the old mint-again renewal logic was re-implemented in isolation and run against the same scenario:

// old (buggy) renewal, isolated for comparison only fn old_renew(table: &mut Table, pid: u32, now_ns: u64) -> usize { table.insert(pid, now_ns + LEASE_NS) // mints #2, #1 untouched } live capabilities for pid 500 after mint: 1 live capabilities for pid 500 after 'renewal': 2 (BUG: should still be 1) original capability idx 0 still present: true new orphaned capability idx 1 also present: true 

This confirms the old code really does double the live-capability count on every renewal, and that the fixed renew_attestation (validated above) eliminates that leak entirely.

What did not change

verify_tee_evidence's trust-on-first-use fallback (the let _ = report; branch when no TEE feature is compiled in) is untouched — it's an existing, separately-scoped simplification for host/dev builds, not something this cleanup was asked to address.

capability::renew_attestation's own behavior (extend in place, don't touch the FIX-H2 generation counter) is unchanged; this patch just makes attestation.rs actually call it, instead of routing around it through a duplicate mint.

AttestationReport is unchanged — still a plain evidence struct with no behavior of its own.
