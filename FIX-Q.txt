FIX-Q — Real TLA+/TLC Verification of Safe-Bypass Liveness

Status: Downloaded and ran the real TLA+ model checker (TLC 2.19) against a completed version of formal/MicrokernelScheduler.tla. This closes the one boundary QIB-muK_FIX-K_safe_bypass_watchdog.md explicitly flagged as unexecuted — and, in doing so, surfaced two genuine defects in the original document's TLA+ artifact itself, independent of anything in the Rust implementation.

Setup

curl -sL -o tla2tools.jar \ "https://github.com/tlaplus/tlaplus/releases/latest/download/tla2tools.jar" java -cp tla2tools.jar tlc2.TLC -help # confirms TLC 2.19 of 08 August 2024 

Downloaded cleanly; Java 21 was already present.

Finding #1: the original spec was never actually runnable

The original document's MicrokernelScheduler.tla closes with:

THEOREM Spec => /\ []TypeOK /\ QubitCapTaskProgress /\ []DeterministicFallback /\ SafeBypassEscapable /\ []BoundedMathTermination /\ []CapRevocationSafety /\ []AttestationLeaseRespected 

But nowhere in the file is Next or Spec ever defined — only Init. This isn't a subtle issue; running the text verbatim through TLC fails immediately:

Semantic errors: line 76, col 9 to line 76, col 12 of module MicrokernelScheduler_ORIGINAL Unknown operator: `Spec'. Error: Parsing or semantic analysis failed. 

Every invariant and property in that THEOREM — including SafeBypassEscapable, the one FIX-K's write-up specifically wanted checked — was therefore never mechanically verified at all in the original artifact. The THEOREM was aspirational text, not a checked claim. This patch adds the missing Next action relation and Spec definition, including the FIX-K-specific WatchdogReset action proposed but never written in FIX-K's own deliverable.

Finding #2: SafeBypassEscapable itself was too weak to mean what it claimed

After adding Next/Spec, a first TLC run against the old (pre-FIX-K) design — with WatchdogReset removed entirely, modeling the original "spin forever, nothing can ever clear safe_bypass" panic handler — reported:

Model checking completed. No error has been found. 

That's wrong on its face: the old design is exactly the one FIX-K's write-up demonstrated (via rustc's own unreachable-code lint) can never leave Safe-Bypass. Investigating why TLC didn't catch it revealed the second real defect: the original property text,

SafeBypassEscapable == safe_bypass => <>(\neg safe_bypass) 

has no enclosing []. Without it, TLC evaluates the implication only against the first state of a behavior — and Init sets safe_bypass = FALSE, so the antecedent is already false at state 0, making the whole property vacuously true regardless of what Next does afterward, for any implementation, buggy or not. Both the old and the soon-to-be-fixed design would "pass" this property equally uninformatively. The fix is a one-symbol change:

SafeBypassEscapable == [](safe_bypass => <>(\neg safe_bypass)) 

This is what actually encodes "at every point the system enters Safe-Bypass, it must eventually leave" — the property the surrounding prose always claimed, but the original formula never actually stated.

Proving that pass is meaningful: the pre-FIX-K design genuinely fails

To confirm SafeBypassEscapable isn't just passing because the check is too weak in some other way, the identical spec was re-run with WatchdogReset (and its fairness condition) removed entirely — modeling exactly the old panic handler: safe_bypass becomes TRUE and nothing in the system can ever set it back:

java -cp tla2tools.jar tlc2.TLC -config MicrokernelScheduler_OLD.cfg MicrokernelScheduler_OLD.tla

EnterSafeBypass fires at state 5; every subsequent state — through capability grants, revocations, and ticks — keeps safe_bypass = TRUE forever, ending in a genuine lasso cycle (state 13 → 14 → 13 → ...) where it never becomes FALSE again. This is exactly the property violation FIX-K's write-up predicted from first principles (rustc's own unreachable-code lint on the old diverging panic handler); TLC now confirms it mechanically, with a concrete counterexample trace, against the corrected property. The completed spec with WatchdogReset (validated above) closes exactly this hole.

What the model abstracts, and what it doesn't prove

State space is finite by construction for model checking. Tasks, MaxDeadlineNS, and MaxMathIterations are small constants ({t1, t2}, 3, 2), and a StateConstraint caps current_epoch <= 3 since it's declared \in Nat (unbounded) and RevokeCap can increment it forever otherwise. TLC's own warning about state constraints during liveness checking is exactly why Finding #2 was checked as carefully as it was: a constraint can mask a real liveness violation if it happens to cut off the only counterexample path. That's precisely why the old design was re-run under the identical constraint and still produced a genuine counterexample — confirming the constraint isn't hiding anything here, at least at this abstraction level and these constant values.

This spec does not model FIX-H2's blast-radius property. RevokeCap(t) in this abstraction only clears t's own capability — it was never written any other way, so this model can't distinguish the "one task's cap revoked" design from the old "everyone's cap revoked" bug the way the real Rust code needed to. FIX-H2's actual guarantee was (correctly) validated with real Rust tests in its own deliverable, not here; this TLA+ model's CapRevocationSafety is a much weaker statement ("if dispatched, must hold a cap") that both designs would satisfy.

WatchdogReset's state-reset choices are a modeling judgment call, documented inline in the .tla file: a reset clears dispatched and has_qubit_cap for everyone (mirroring a cold boot with no capabilities yet minted) but leaves current_epoch and math_iters alone, since those are properties of the code rather than memory a physical reset would need to zero. A different, equally defensible modeling choice might reset those too; this doesn't change whether WatchdogReset existing and being weakly-fair is what makes SafeBypassEscapable hold.

What this closes

QIB-muK_FIX-K_safe_bypass_watchdog.md's validation section stated: "no TLC model-checker is reachable in this sandbox, so the TLA+ spec itself was not mechanically re-verified." That's no longer accurate — it was downloaded, the spec was completed (fixing two real defects found only by attempting to run it), and both the fixed design's compliance and the old design's genuine violation were confirmed by actual TLC output, not reasoning about what TLC would presumably find.
