FIX-P — A Real Test for FIX-D's Mutex Poison Recovery

Status: Implemented, compiled, and test-validated (5/5 tests passing on Rust 1.75, cargo test), including a genuine, visibly-panicking poisoning of a real std::sync::Mutex and confirmation that the state survives it. Rust core only — see "Scope and honesty about validation" for the PyO3/pytest boundary.

The gap

FIX-D correctly replaced STATE.lock().unwrap() with:

STATE.lock().unwrap_or_else(|poisoned| poisoned.into_inner()) 

so a panic while holding the lock can't permanently crash the routing backbone. That code was fine. Its test was not:

# OLD test_breaker_accessible_after_poison_recovery def test_breaker_accessible_after_poison_recovery(self): """Simulate a scenario that would previously poison the Mutex. Subsequent calls must succeed (poison handled with into_inner).""" for _ in range(10): qib.record_reality_delta(0.10) state = json.loads(qib.get_circuit_breaker_state()) assert "ai_routing_enabled" in state, "Circuit breaker must be accessible" 

Nothing in this test ever panics while holding the lock. It calls the normal, healthy code path ten times and checks the state is accessible afterward — which it always is, whether or not unwrap_or_else exists at all. A minimal repro of what the old, unfixed design (STATE.lock().unwrap()) would actually do against a real poisoning confirms the gap directly:

get_learning_rate_old() PANICKED after poisoning -- exactly what FIX-D exists to prevent 

The old design panics on every call after a real poisoning, exactly as expected — and the original test would never have noticed, because it never created that condition in the first place.

The fix

Add debug_poison_state_for_test() — a test-only hook that genuinely poisons STATE: spawns a thread, locks the Mutex, panics while holding the guard, and joins (swallowing the resulting JoinError, which is expected). Rewrite the test suite (Rust-level here, and the corresponding Python file) to actually call this hook before checking recovery — the thing the original test's name claimed to do but didn't.

Confirming the old design really would fail

// old (unfixed) design, isolated for comparison only fn get_learning_rate_old() -> f64 { *STATE.lock().unwrap() // no poison recovery } get_learning_rate_old() PANICKED after poisoning -- exactly what FIX-D exists to prevent 

This confirms, end to end: a real poisoning genuinely breaks the unfixed design on the very next call, FIX-D's unwrap_or_else genuinely prevents that (validated above), and the original Python test could never have told the difference between the two because it never created a real poisoning to distinguish them.

Scope and honesty about validation

This crate compiles and tests the calibration state machine and its poisoning/recovery behavior as plain Rust — no PyO3 dependency, and get_circuit_breaker_state_fields() stands in for the real #[pyfunction]'s JSON-serialized return value as a plain tuple, since this crate has no serde_json dependency either. What's validated above is real: a genuine std::sync::Mutex, genuinely poisoned via a real panic, with real recovery confirmed across single and repeated poisoning events and mid-sequence poisoning.

What is not validated here: the actual PyO3 binding for _debug_poison_calibration_state (which would need to be added to calibration.rs as a #[cfg(feature = "debug-hooks")] #[pyfunction] wrapping debug_poison_state_for_test()) and the corrected tests/test_calibration.py file were not compiled or executed against a real Python interpreter through the actual extension module — building that requires maturin/setuptools-rust and a matching Python ABI, not set up in this environment. The Python file was checked with python3 -m py_compile (syntactically valid) but not run against real bindings. This is the same boundary drawn explicitly in FIX-M's write-up: the logic that can be compiled and tested in isolation was, exhaustively; the PyO3 wiring around it is described precisely but the word "tested" stops at that boundary.

What did not change

FIX-D's lock_state!() macro itself — STATE.lock().unwrap_or_else(|poisoned| poisoned.into_inner()) — is byte-for-byte unchanged. This patch adds a way to genuinely test it, not a change to its logic.

record_reality_delta_internal's Brier-score / circuit-breaker logic (Improvement 2-C) is unchanged.

debug_poison_state_for_test is not reachable from production code paths. It's gated behind #[cfg(any(test, feature = "debug-hooks"))] precisely so it can never be called accidentally from real traffic — the real crate's default feature set should not include debug-hooks.
